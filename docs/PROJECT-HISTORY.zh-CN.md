# 项目历程：思路、问题与解决

日期：2026-09-29。覆盖两个仓库：`coding-harness`（运行时和评测）和 `coding-agent`（记忆）。
写给以后回看这个项目的人，包括面试时需要讲清楚来龙去脉的自己。实验结论的正式版本见 `coding-agent/docs/A5-FINAL-REPORT.zh-CN.md`。

## 0. 一句话

先搭了一个可控、可观测的单 agent coding harness，再想证明"记忆能让 agent 在真实 SWE-bench 题上解得更好"。中途发现 harness 本身解不出题、隔离有漏洞、流程过重，于是转向先把 B0 做到能真实解题，最后在 56 道 SWE-bench Verified 题上完成了一次预注册、答案隔离的对照实验：**B0 解出率 68.5%，注入同仓库历史修复卡片的 B2 没有带来可检出的提升**（平均差 −1.8 个百分点，95% 区间 [−8.3, +4.8]）。这是实验做成功之后得到的否定结论：链路有效，被否定的是这一种记忆设计。

## 2. 起点：两个项目各自的第一版

### 2.1 coding-harness（6 月）

定位是"可控、可观测、可评测的单 agent coding harness"：plan-act-observe 循环，文件和命令工具，路径隔离、命令白名单、预算、超时，JSONL trace，repo 任务和 SWE-bench 子集评测，bootstrap 置信区间，失败分类。6 月下旬按 Solid 路线图分 A、B、C、D 四批加固（`docs/SOLID-ROADMAP.zh-CN.md`），D1 做了 SWE-bench 子集、防作弊和污染探测，D2 做了失败分类、多模型矩阵和演示材料。

这一阶段已经遇到过混淆变量的问题：baseline 和 plan_act 的配置同时改了命令策略，+7.4% 不能归因给 planner，后来补了同策略对照。"控制变量"这条意识从这里开始。

### 2.2 coding-agent（6 月到 7 月初）

RepoSkillAgent 是独立的多智能体项目：PlanAct 任务图、Manager/Locator/Developer/QA 角色、SkillCard、MemoryHint、按任务类别路由注入。过程见 `coding-agent/docs/project-chronology.zh-CN.md`。

关键经历：

- tiny_24 上所有配置 100%，完全饱和，于是做了 hard_12。
- 第一次接真实 DeepSeek，skill 和 memory 注入反而拉低成功率（L3 67%、L4 58%，L2 是 92%）。
- 之后连续做了 gating、domain 过滤、holdout 配对、类别路由，最终在自建的 medium_48 上重复 2 次，L5 80.2% 对 L2 70.8%。

回头看，这个 +9.4pp 有一个结构性前提：自建题集按 support/holdout 成对设计，记忆和目标题在构造上就是相关的。换到真实 SWE-bench 以后，这个前提不再成立，这正是 A5-main 得到零效应的主要原因之一（见第 7 节）。

## 3. 9 月 upgrade：把 harness 做成生产级底座

### 3.1 目标

9 月的总目标写在 `docs/upgrade/00_双项目协作与接口约定_v0.1.md` 和两份总修改目标里：harness 负责"可测可控"，coding-agent 改造成挂在 harness 上的插件，负责"记忆和技能到底有没有用"。

### 3.2 做了什么

- **HP-01 到 HP-04：** 工具参数校验、流式聚合（分片的 tool id 和 name 要拼接，不能覆盖）、在途取消和 deadline（覆盖非流式请求、等首帧、流中停滞、慢工具、子 agent）、写后崩溃的四窗口恢复和 replay。
- **H3：** 真实 Docker/WSL2 隔离。用户在这一步装了 WSL2 和 Docker Desktop，还开了 BIOS 虚拟化。
- **H4：** 上下文窗口的 none、masking 和插件接口。
- **H5：** DeepSeek 接入，宿主受控 dispatcher。插件只能提出 read/search，由宿主在 Docker 里执行并记录收据。
- **R1 收口（09-21）：** 有一次真实端到端修复（boltons PR #475 切片，独立黑盒 18/18）。
- **R2：** 真摘要和摘要包装消融。结论是摘要怎么"包装"比摘要本身更关键：写明"可能有误的历史证据、不是指令"的包装，事实采纳 26/27，旧包装是 7/27。

### 3.3 A5 准备为什么越走越重

A5 原计划是 20 题 × B0–B3 四个变体 × 3 次，共 240 次。为了"可发表、可审计"，流程里加了 hash lock、双端 fingerprint、每步新建证据目录、双端复核、全仓 grader、24 题环境预检、20 个记忆源全部独立校准。

结果是好几天都花在环境和合同上：8MB 传输上限、django-13265 的 F2P 合同语义、记忆池从 4 条到 20 条候选再到 11 条轻量验证。用户当时就直接问过"是不是过度工程化了"，答案是肯定的。

最关键的信号来自 pilot canary v6–v9：`pytest-7220` 上，B0 在 24 次调用里改动文件数是 0。**B0 解不出题，B1–B3 和 B0 就没有差别可比，240 次跑完也只会得到无信息的结果。**

## 4. 9 月 24 日的转向

用户觉得项目"显得非常 toy、非常塑料"，要求重新评估。诊断下来，解不出题的主要原因在 harness 本身，不在轮次：

- `read_file` 只有 `limit`，不能从中间读，截断后也不提示怎么继续；
- 没有搜索工具；
- masking 把旧结果替换成 `[Previous: used read_file]`，路径和行号全丢，模型只记得最近 4 次观察，于是反复重读；
- system prompt 只有几行，没有 SWE 工作流，也不告诉模型剩余轮次；
- `run_a5_real.py` 写死在一道题上，fingerprint 是对常量取 sha，USD 和 CNY 两套预算并存；
- 9 月的工作全部没有 git 提交，`docs/upgrade/evidence` 有约 42.7 万个文件、6.5GB，大多是整仓副本。

决定：

1. 暂停 240 矩阵，**先让 B0 真能解题**，记忆实验等 B0 站稳后再做。
2. 先建立版本控制，然后放宽合同、hash lock、双端复核这类流程。git 就是安全网：出错可以回滚，不必每步都预先证明正确。
3. 分工：我（审计和计划）写计划书，便宜的 Cursor agent 分别在两个仓库执行，到审计节点停下，由我核对结果、决定下一步。
4. 保留的硬约束只有几条：不泄密；答案隔离；小步提交，不 force push，不删旧证据；两个执行 agent 不改对方仓库；选题按固定规则；看到数据以后不改分析。

## 5. 冲刺各轮

### 第 1 轮（09-24）：工具和上下文

- 通用单题运行器 `run_swe_task.py`，dev 集，预算统一为 CNY 账本（单次 1 元）。
- `read_file` 加 offset 和行号，新增只读 `search_code`，masking 保留路径、offset 和退出码，SWE prompt，剩余调用提示。
- 顺带修了嵌套 profile 找不到 `.env` 的问题：之前真实调用发出去的 Bearer 是空的。
- 结果：pytest 三道 dev 题 0 解出，但 5103 第一次出现了代码改动。grader 给出 invalid_env，暴露出 grader 本身不可靠。

### 第 2 轮（09-25）：镜像和 grader

- `export_delta` 用 gold 文件做白名单：agent 只要碰了 changelog，整份 delta 就被丢掉。改成对比整棵树，收集全部改动。
- `BaselineImageBackend`：从镜像的 `/opt/repo` 复制到 `/workspace`。
- `ImageGrader`：在同一个镜像里应用 delta，再用 test patch 覆盖测试文件，按 nodeid 收据判定，不看退出码。
- dev 集校准成 12 题，要求空改动 F2P 失败、gold 通过。
- B0 在 12 题上解出 6 题。**这个数字后来被证明是在测试可见的条件下得到的。**
- 我的计划里写了 thinking 对照，但 thinking 链路从来没实现过，执行侧如实停下。这是计划的失误，之后 thinking 一直不做。

### 第 3 轮（09-25）：修链路，发现泄漏

- sklearn 的 `.so` 被换成符号链接，导出时跳过了链接，原文件就被记成删除，grader 应用这份删除列表后 import 失败。修复：导出和应用都跳过编译产物。
- step deadline 杀掉了容器，于是没有导出，出现 `delta_lost`。修复：命令超时不拆容器，运行结束时先导出。
- 14 题 dev 集，冻结 `b0-v1`，3 次重复解出 32/42。
- **审计时发现答案泄漏**（`AUDIT-3-CORRECTION.zh-CN.md`）：dev 镜像是用 `baseline.tar.gz` 构建的，它等于原始代码加 test patch，所以 agent 的工作区里就有 F2P 测试。sympy-11400、sklearn-10949、django-11039 的轨迹里，agent 都直接搜到并运行了隐藏测试。
  - 根源在第 2 轮计划只写了"参照 preflight 从 `/opt/repo` 复制"，没有核对 `/opt/repo` 里装的是什么。这是我的计划错误，执行侧和 Codex 的审计也都没发现。
- 同时发现 pilot 校准"0/20 接受"的原因是镜像不对：大多是 known-good 镜像，gold 已经打在里面，空改动和 gold 的结果完全相同。旧校准从来没检查过"空改动会失败"。

### 第 4 轮（09-25 至 26，计划由 Codex 按矫正文件写）：干净镜像

- 从 original 源码构建干净镜像，不放 test patch 和 gold patch；运行前比对源码 hash，并做全文件系统扫描。
- 校准增加"gold 必须改变结果"。
- `b0-v2` 在同样 14 题上解出 17/42；一次 `StoreError` 重跑后是 18/42。**测试可见时是 32/42，隔离之后掉到 18/42**：泄漏让解出率虚高了将近一倍。

### 第 5 轮（09-26 至 28）：A5-main 设计和题目池

**设计（`A5-MAIN-DESIGN.zh-CN.md`）：**
- 统计功效主要取决于题目数，变体数不增加功效。所以放弃 240 矩阵，改成最多 60 题 × B0/B2 × 3 次。
- 按时间顺序做留一法：只注入同仓库、更早、已验证解出的源题卡片。
- 主要指标是配对的 d_t，用符号翻转检验和 bootstrap 区间。区间包含 0 时只能写"没有检出大于 X 的效应"。

**题目池：** SWE-bench Verified 5 个仓库，按 `created_at` 等间隔各取 12 道，共 60 道。环境原因剔除 4 道，合格 56 道。
- 官方 SWE-bench 镜像试了 3 道，没有全部通过校准，于是用 v4.0.4 的 specs 自建。
- 环境问题一长串：Python 3.5/3.6 要用 Debian archive；老 sklearn 要 pin Cython；编译需要补头文件；Windows 下不能创建符号链接；Django 测试名被截断，sympy 测试要映射到定义它的文件，pytest 的 id 被逗号拆开；sphinx 要装 roman；pytest 要从题目自己的源码树安装。
- Docker 数据盘在 C 盘，空间不够，用户手动迁到 E 盘。

**agent 侧：** 卡片加上 `created_at`；通用构建脚本；分析脚本在看到任何真实数据之前写好，并用合成数据测试。

**第 5 轮补丁（审计发现的偏移）：**
- mock 输出写进了正式目录；
- 时间过滤只读 dev 交接、用字符串比较日期，还会静默回退；
- Django docstring 形式的测试 id 被丢掉（15022 的 F2P 从 3 条变成 1 条）；
- 扫描排除规则太宽。

### 第 6 轮（09-28 至 29）：冻结和正式运行

**6A：** 冻结 `a5-main-freeze`。canary 里 sphinx-8593 在调用模型之前 isolation 就失败了：构建时跳过了被 `pre_install` 用 sed 改写的文件，运行时却还在比对。修复：重放 sed，得到期望 hash，构建和运行用同一份 override。sphinx-9258 另有 `grep -q` 守卫的 sed，补了规则。
- 新增零花费 preflight：镜像、隔离、源码 hash、nodeid、工具冒烟、prompt 内容。
- 调整 infra_error 停止线（满 3 次且超过 10%）。
- 冻结修订 1。

**6B：** B0 开跑后，Python 低于 3.9 的镜像里结构化工具全部报错（`Path.is_relative_to`），影响 17 道题、25 次运行中的 22 次。dev 镜像都是 Python 3.9，所以之前没暴露出来。
- 修复工具兼容性，preflight 加工具冒烟，Docker 控制通道出错时重试，`harness_tool_errors` 设为停止条件。
- 25 次运行作废（13.7 元），冻结修订 2。

**6C：** 修订 2 以后 36 次有效运行 **0 解出**。用户问"这符合预期吗"，答案是不符合。
- 根因：题目池的 prompt 里没有 issue 文本，只有 `Public issue for <id>` 占位。选题脚本没带上 `problem_statement`，运行器静默回退成了占位符。
- 这是我在第 5 轮审计时漏掉的：只看了代码路径，没看实际渲染出来的 prompt。
- 修复：补齐 issue 原文；所有静默回退改成报错；preflight 渲染每道题的 prompt，检查 issue 原文和私有内容。
- 新增故障警报：正式运行满 30 次仍 0 解出就停。
- 38 次运行作废（24.1 元），冻结修订 3。
- 随后 B0 一次跑完：**115/168 = 68.5%**。

**6D：** B0 交接 v2（带 isolation、base commit、issue sha）。4 次 delta_lost 查清楚了：3 次是 agent 自己撤回改动，1 次是 search 等于 replace 的空编辑。
- 新增漂移对照臂：B2 期间在同一队列里混跑一轮 B0 r4，种子 20260929。
- 预测注入表（51/56 道题会注入）先提交，再开跑 B2；实际注入和预测不一致就停。
- agent 侧建 v6 卡片：70 张，50 张 validated_fix 加 20 张 failed_attempt；来源题测试命令里的 4 处 id 换成 `[hidden-test]`。我审计后通过。
- B2 途中停了三次：
  - 第一次是一致性核对代码没读到存成附件的负载，只改核对代码，结果不变；
  - 第二次是 django-13964 B2 r3，候选删掉了外键赋值分支，`setUpClass` 报错，37 个 id 都没跑。新规则：同一镜像用空改动重评，和校准一致就记为普通失败；
  - 第三次是 sphinx-7590 B2 r3，候选代码死循环导致测试超时，规则扩展到执行超时。
- 最终 B2 168/168，r4 56/56，注入 168 次全部和预测一致，没有晚于目标、目标自身或跨仓库的卡。

## 6. A5-main 结果

| 指标 | 数值 |
| --- | --- |
| B0 解出率 | 115/168 = 68.5%（django 72.7%，pytest 80.6%，sklearn 86.7%，sphinx 60.6%，sympy 44.4%） |
| 主要分析（56 题） | 平均 d_t −0.018，p = 0.72，95% 区间 [−0.083, +0.048] |
| 次要分析（预测注入的 51 题） | 平均 d_t 0.000，区间 [−0.065, +0.065] |
| 漂移（r4 减 r1–r3） | −0.024；B2 减同期 r4 是 +0.006 |
| 每次花费 / 调用 / 首次编辑轮次 | B0 0.329 元 / 23.6 / 10.2；B2 0.340 元 / 23.7 / 9.7 |

按预注册的写法，结论是"没有检出大于 13.1 个百分点的效应"。从区间看，ITT 效应大于约 +5 个百分点的可能性可以排除。

案例层面的原因（明细在 `docs/sprint/A5-CASE-DATA.md`，叙述见最终报告第 7 节）：

- 51 道注入了卡片的题里，只有 9 道的卡片提到了正确的修改文件，而且都是通用文件。这 9 道的 B0 全部是 3/3 或 0/3，其中 8 道 d_t = 0；
- 153 次注入了卡片的运行里，只有 5 次打开过卡片独有的文件，没有一次在那里做最终修改；
- 变化最大的几道题都能用随机性解释：sphinx-9673（3/3→1/3）六次都改对了同一个函数，成败只在一两行写法；sphinx-9258（1/3→3/3）卡片与 gold 文件无关；django-13964（2/3→0/3）卡片无关，连续三次失败大约是 1/8 的概率；
- 5 道未注入卡片的题平均 d_t 就是 −0.20，其中 3 道从 3/3 掉到 2/3。没有任何记忆，单题 ±1/3 也会出现；
- 34 道题 3/3、13 道 0/3，能提升的空间只在 22 道题上。

## 7. 问题与解决汇总

| 类别 | 问题 | 怎么发现的 | 解决 |
| --- | --- | --- | --- |
| 答案隔离 | 镜像里带 test patch，agent 能搜到并运行隐藏测试 | 第 3 轮审计读轨迹 | 干净镜像、源码 hash、全文件系统扫描、运行前检查 |
| 答案隔离 | known-good 镜像里已经打了 gold，校准毫无意义 | 空改动和 gold 结果完全相同 | 校准必须满足"gold 改变结果" |
| 答案隔离 | sed 改写过的文件，构建和运行的比对口径不一致 | canary 在调用模型前失败 | 重放 sed 得到期望 hash，构建和运行共用 override |
| grader | gold 白名单导出丢掉整份 delta | 改过代码却显示没改 | 整树对比导出 |
| grader | `.so` 被记成删除，测试无法 import | P2P 全部变成 0 | 跳过编译产物 |
| grader | 候选改坏测试框架或死循环，结果显示 missing | B2 停止 | 空改动重评，和校准一致就记为普通失败 |
| 数据 | prompt 里没有 issue 文本 | 36 次运行 0 解出 | 补齐原文，静默回退改报错，preflight 渲染检查 |
| 数据 | Django docstring 测试 id 被丢 | 审计核对 F2P 条数 | 用 AST 映射回测试方法 |
| 数据 | 时间过滤静默回退、用字符串比较日期 | 审计读代码 | 带时区比较，缺日期就报错 |
| 工具 | Python 3.6/3.8 镜像里工具全部报错 | B0 grader 超时后排查 | 兼容写法，preflight 工具冒烟，`harness_tool_errors` 作为停止条件 |
| 工具 | step deadline 杀掉容器导致没有导出 | delta_lost | 超时不拆容器，结束时先导出 |
| 流程 | 用 profile 名判断是否用干净镜像 | 第 4 轮审计 | 没有干净镜像就拒绝运行 |
| 流程 | mock 输出混进正式目录 | 第 5 轮审计 | 按模式分目录，续跑前核对 |
| 统计 | 240 矩阵功效低 | 功效估算 | 把钱花在增加题目数上 |
| 统计 | 时段漂移可能被当成效应 | 设计复核 | 混跑 B0 r4 作为漂移对照臂 |

## 8. 这种记忆为什么没用，以及主流设计为什么搬不过来

正式报告的第 7、8、10 节会展开。这里只保留讨论的骨架，方便以后回看时不必先读完整报告。

### 8.1 这次记的是什么

B2 注入的是同一仓库、`created_at` 更早、B0 已解出的题目的规则提取卡片（改了哪些文件、过程叙述、测试命令）。检索是 BM25 加路径加分，被动放进 prompt，模型没有记忆工具。这是"跨任务经验"的一个弱化版本：异质任务、规则提取而不是 LLM 提炼、被动注入。

### 8.2 机制

1. **相关性低。** 51 道注入题里只有 9 道的卡片提到 gold 文件，还都是通用文件。SWE-bench 同一仓库的题横跨多年、落在不同子系统，"更早的修法"很少能直接迁移。
2. **记的是具体修法，不是可迁移策略。** approach 是 agent 中途的自述。对已经能解出 68.5% 的模型，"先复现再修改"这类通用策略它本来就会。
3. **瓶颈往往在细节，不在定位。** sphinx-9673 的 6 次运行都改对了 `augment_descriptions_with_types`，成败只在一两行。这个判断来自少数案例，没有对全部失败运行做统计。
4. **被动注入，模型不理会。** 153 次里 5 次打开过卡片独有文件，0 次最终改在那里。调用次数和首次编辑轮次几乎不变。
5. **天花板。** 34 道 3/3、13 道 0/3。文献里 SWE 记忆工作报告的也多是个位数提升，低于本设计大约 9 个百分点的检出下限，所以否定结论和那些小幅正向报告并不矛盾。

### 8.3 主流 agent 记忆

| 类型 | 代表 | 记什么 | 什么情况下有效 |
| --- | --- | --- | --- |
| 项目规则 | CLAUDE.md、AGENTS.md、Cursor rules | 约定、构建和测试命令、已知坑 | 每次加载，内容少而稳定 |
| 用户或会话记忆 | ChatGPT memory、Mem0、MemGPT/Letta | 偏好、长对话事实 | 个性化，和修代码正确率关系不大 |
| 同任务反思 | Reflexion | 同一题上次为什么失败 | 重试同一题，有失败信号 |
| 跨任务经验和策略 | ExpeL、Agent Workflow Memory、ReasoningBank | LLM 从成败轨迹里提炼的抽象策略 | 任务同质、流程可复用（同一网站、同一类题） |
| 技能库 | Voyager、Claude Skills | 可执行的代码或流程 | 同一种操作反复出现 |

有效的前提基本是两条之一：记忆和当前任务高度相关，或者记的是稳定的项目知识。本实验两条都不满足。Agent Workflow Memory 在 WebArena 上收益大，是因为登录、搜索这些流程会反复出现；那不是 SWE-bench 跨 issue 的情况。

早期 RepoSkillAgent 在 medium_48 上 L5 比 L2 高 9.4 个百分点，是因为 support/holdout 按类别成对构造。换到按时间顺序抽样的真实基准，这个前提没了，两个结果并不矛盾。

### 8.4 若以后另开实验（本项目不做）

- **优先：同题重试（Reflexion 式）。** B0 的 53 次失败可以直接当第一次尝试。R0 从头再做，R1 带上第一次摘要；失败信号只给"上次没通过"这 1 比特。约 212 次、约 70 元。这是唯一保证记忆 100% 相关的设定。
- 备选：项目规则记忆，主要看调用次数、花费、首次编辑轮次。
- 备选：LLM 提炼策略，配更弱模型或更同质的任务序列。成本高，预期信号弱。

## 9. 经验

1. **先证明 baseline 能解题，再做对照。** B0 解不出题时，任何变体比较都没有信息量。9 月前半段的主要时间损失就在这里。
2. **答案隔离要检查镜像里实际装了什么，不能只看 prompt 和代码路径。** 泄漏让解出率从 18/42 虚高到 32/42。
3. **静默回退是最危险的 bug。** issue 占位符、时间过滤回退、按 profile 名选择镜像，都属于"不报错但结果错"。所有回退都应该改成报错，并在花钱之前把真实输入渲染出来检查。
4. **结果过于整齐本身就是信号。** 0/36、空改动和 gold 结果完全相同，都是链路坏了，不是题目难。后来把这类信号直接写成停止条件（故障警报）。
5. **冻结、修订、作废。** 发现问题就作废受影响的运行，不混进分母；旧证据移走但保留；每次规则变化写冻结补记，说明对已完成运行的影响。
6. **统计功效靠题数；分析要预注册；要有漂移对照。** 这让一个零结果也能有信息量：它能排除大于约 5 个百分点的效应，而不是一句"不显著"。
7. **严谨和过度工程化的界线在于：约束是不是在挡住真实风险。** 答案隔离、预注册、作废规则挡住了真实风险；hash lock、双端复核、每步新建证据目录主要在消耗时间。有了 git 作为安全网以后，后者可以大幅放宽。
8. **审计要看真实产物。** 我的两次重大漏判（第 2 轮没核对 `/opt/repo`，第 5 轮没看渲染后的 prompt）都是只看了计划和代码，没看实际数据。
9. **记忆能不能起作用，先看相关性。** 自建题集里记忆和目标题在构造上相关，所以有 +9.4pp；真实 SWE-bench 里跨 issue 的相关性很低，强模型也基本不看卡片，所以是零效应。详见第 8 节。

## 11. 协作方式

- 我负责审计、计划、实验设计和结论把关，Cursor agent 分别在两个仓库执行，每轮到审计节点停下。第 4 轮计划曾交给 Codex 写，它按我的矫正文件完成得不错；之后因为模型质量问题又回到这边。
- 所有计划书放在各仓库的 `docs/sprint/`，执行记录只追加到 `PROGRESS.md`，每个审计节点有 `CHECKPOINT-N.md`。
- 两个执行 agent 通过交接文件（带 sha256，LF 归一化）传递数据，不直接改对方仓库。
