# 双项目协作与接口约定 v0.1

日期：2026-09-18。状态：总体目标中的初始契约，供两个项目制定实现计划；不是已经实现的 API。字段语义与职责边界应保留，具体 Python 签名、文件组织和传输方式可在实现计划中调整并说明理由。

## 1. 用户目标与本轮授权

用户正在准备第一份国内大厂日常实习，主语言 Python，目标是 Agent Runtime/Harness、Agent Infra 应用侧、Coding Agent 和 Agent Evaluation。两个项目应组成一套能独立演示、解释源码、复现实验的作品集。

本轮任务是建立目标、理解差距、生成实施计划，尚未决定由 Codex 直接实现还是由 Cursor 按计划实现。因此收到交接后：

- 阅读总目标和本契约，检查当前代码与未提交修改，产出分阶段实施计划和首批任务包。
- 可以把收到的三份目标文档保存到自己仓库的 `docs/upgrade/`；存在同名文件时先检查差异，保留用户修改。
- 暂不修改产品源码、不启动付费模型实验、不大规模下载 benchmark、不自动提交或推送。
- 用户后续明确要求开始某阶段后，常规实现、相关修复和验证应连续完成，不要每个文件都重复问批准。
- 不要因文档中存在“最终要实现的功能”就把整份路线图当作本轮立即实施指令。

## 2. 责任分配

| 范围 | coding-harness | coding-agent |
|---|---|---|
| 模型请求、连接池、streaming、取消与使用量 | 主实现与统一计量 | 接入，保留旧 client 仅供明确标注的 legacy 实验 |
| 工具执行、权限检查、进程清理、容器 | 主实现 | 只通过受控 adapter 调用，不复制执行内核 |
| 会话事件、checkpoint、恢复、artifact 存储 | 主实现 | 维护自身可序列化策略状态，提交事件候选 |
| 模型上下文窗口、masking、摘要、offload | 主实现与对照实验 | 输出带来源的 skill/memory 候选，不绕过窗口预算 |
| Skill、Memory、失效规则、策略路由 | 提供可插拔接口，不内置具体修复经验 | 主实现与消融实验 |
| 未知 issue 定位、候选证据、修复策略 | 通用工具和运行循环 | 主实现与质量评价 |
| 运行时评测、资源记录、结果存储 | 主实现 | 使用公共结果格式，提供修复/记忆专用指标 |
| 外部基准任务选择及实验协议 | 运行环境、统一 grader 接口 | issue 任务 manifest、记忆来源与 split |
| 集成故障 | 修服务端语义和通用能力 | 修客户端映射和策略假设 |

两边可以各有 CLI 和测试；不能各自再建一套资源预算、容器平台和通用 runtime。暂时保留旧路径比立即大改到一个单体仓库更合适。

## 3. 集成策略：先独立完成，再用小契约连接

第一阶段两仓库分别用本地 fixture/stub 开发；任何一边未完成，都不应阻止另一边修已有问题。目标是在两个核心模块稳定后完成一个真实连接演示。

推荐最终主路径：harness 拥有执行循环与安全边界，agent 提供策略增强插件。现有 inspect→locate→patch→test 图可以作为策略实现或兼容 runner，不能因此绕过统一的工具、模型和预算入口。

首个接口优先使用版本化 JSON 数据结构，避免跨仓库导入对方内部类。Python Protocol、独立子进程 JSONL、可选依赖 adapter 均可；计划中选最小方案。两个包均可在不安装对方时运行单元测试。不要为了连接两个本地仓库先引入服务发现、队列集群或微服务。

同一真实任务中只能有一个预算权威、一个有序事件写入器。插件若需要额外 LLM 调用，须走宿主的受控调用入口，或事先生成并在实验中计入构建成本，不能隐藏直连模型的开销。

## 4. 最小公共数据契约

所有跨仓库记录带 `schema_version`。以下是需要支持的语义，不要求机械照抄类名。

### 4.1 TaskEnvelope：执行方可见任务

- `task_id`、`task_family`、`issue_text`。
- `repo_ref`：来源、固定 base commit 或本地快照 hash；不使用用户工作目录作为可任意删除的临时仓库。
- `public_context`：公开复现步骤、允许读取的日志和测试线索。
- `workspace_id`、允许的工具集合与执行 profile 引用。
- `budget`：总时限、模型调用/重试上限、token 上限、可选货币上限及币种。
- `protocol_mode`：`realistic` 或 `diagnostic_oracle`；mode 必须进入 trace/report。
- `seed` 与 `repeat_id`：记录实验组织随机性；provider 不支持 seed 时不得声称模型完全确定性。

禁止字段：gold patch、hidden test 内容、expected_files、benchmark category 答案标签、目标任务的未来解决轨迹。它们只能保存在独立 `EvaluationSpec`，不得通过嵌套元数据、日志或文件名旁路进入策略。

任务描述本身公开提及某文件属于正常证据；禁止的是把 benchmark 的额外答案字段偷偷暴露。

### 4.2 RunEvent：单次运行事件

- `schema_version`、`event_id`、`run_id`、`task_id`、每个 run 单调递增的 `seq`。
- UTC 时间戳和用于计时的单调时钟耗时；跨进程不把单调时钟绝对值当作统一时间。
- `step_id`、可空的 `parent_step_id`、`operation_id`、`attempt_id`、可空的 provider `tool_call_id`。
- `event_type`：例如 run.started、model.started/completed/failed、tool.intent/started/completed/failed、context.compacted、memory.selected/rejected、run.finished。
- `payload` 或受控 `artifact_ref`；输入/输出 hash、错误类型、usage 和脱敏版本。

稳定 operation_id 标识同一逻辑动作，重试生成新 attempt_id。持久存储的写入顺序才是事件顺序依据，不依赖并发线程完成时间排序。插件返回候选事件，由宿主统一分配序号和落盘。

### 4.3 工具结果与执行后端

工具请求至少包含：工具名、validated arguments、operation_id、deadline、资源/权限 profile。工具注册时声明 `read_only` / `idempotent_write` / `non_idempotent`，并说明重试和 reconciliation 支持。

结果区分：`succeeded`、`failed`、`cancelled`、`timed_out`、`blocked`、`outcome_unknown`。命令还要有 exit_code、输出 artifact、截断标志、cleanup 状态。`outcome_unknown` 表示可能已有副作用但结果未确认，不能自动重新执行写操作。

后端能力至少声明 cancel、process_cleanup、filesystem_isolation、network_control、resource_limits 是否支持。不支持的能力应报 unavailable 或明确降级，不能从容器静默回退到宿主执行。

### 4.4 PolicyInput / PolicyDecision：最小策略插件接口

PolicyInput 包括：公开 TaskEnvelope、当前目标/计划、已观察的脱敏结果或 artifact 引用、已读文件证据、当前仓库版本、剩余预算、插件上次状态。不得包含 EvaluationSpec。

PolicyDecision 输出：候选上下文片段、来源/有效性信息、选择或拒绝理由、优先级、插件状态和度量事件。读取额外代码或请求额外推理时，以受控 action proposal 提交给宿主；proposal 必须经过工具策略和预算检查。

宿主有权裁剪或拒绝注入，且记录 requested 与 actually_injected 两套数据。插件异常可 fail-open 到无增强基线，但必须报告 `policy_error`；fail-open 不能绕过工具安全策略，也不能把故障实验算作正常 method run。

首版只要求无记忆插件与一个 RepoSkill 插件可替换；多 agent 调度与复杂 advisor 接口留到后续。

### 4.5 ArtifactRef 与 Usage

ArtifactRef 包含 logical id、内容 hash、媒体类型、大小、归属 run、受控相对路径/解析引用和敏感性标记。路径不可由模型任意拼接访问其他 run；外置工具输出有容量限制、读取权限和保留策略。

Usage 区分 provider-reported tokens、estimated tokens、unknown usage；分别记录主模型、摘要、记忆构建、检索 controller、grader 成本。价格表、币种、版本、cache/reasoning 字段缺失情况要可追踪；未知费用不能记成 0。

在线运行预算覆盖该 run 的所有模型调用。离线记忆构建成本单独记录，并同时提供“本次线上成本”“构建成本”“预先固定摊销规则下的总成本”，不任意选择最有利的口径。

### 4.6 RunResult / EvaluationResult

RunResult：终止原因、最终回答、patch/artifact、资源使用、trace 引用、能力 profile。模型停止正常不等于任务成功。

EvaluationResult：独立 grader 的 pass/fail/partial/invalid_env、测试采集数与通过数、回归保持、证据引用。保留 assigned task 全分母，环境失败单列，不能为提高通过率在事后删除失败样本。

## 5. 数据与评测边界

Agent 可见 workspace 与 grader 保留数据应分开，隐藏测试在 agent 停止后才由外部验证环境运行；仅“不给模型 prompt 传字段”不足以防止 shell 读取答案文件。

跨任务记忆写入需要来源声明。可用于未来记忆的验证结果只能来自协议允许的公开测试/证据；私有 grader 的结果不自动成为模型下一轮可用的训练标签。否则必须作为另一种协议单列。

统计主键建议为 `(experiment_id, task_id, variant, repeat_id)`；中断重跑保留 attempt 关系，不能覆盖失败后把重跑计作原先的一次成功。

## 6. 契约验收 fixtures

两边的实施计划应共享一份版本化 fixture 和预期结果，至少涵盖：

1. 正常 read→patch→public test→独立验证，能按 run_id 串起全部证据。
2. 非法工具参数未执行任何工具，返回可解释错误。
3. 取消后无后续写操作；后端不支持该保证时，能力声明和结果不能假装成功。
4. 写操作后、结果落盘前崩溃：进入核对或 unknown，不能重复追加。
5. 有效经验被注入；API 版本改变后经验被拒绝，并保留原因。
6. realistic 输入携带 oracle 字段时明确拒绝/净化并出审计记录；gold 不可被 agent 工具读取。
7. 插件提供很长文本：预算拒绝或裁剪有记录，基础任务仍按规则执行。
8. 未知 schema major version 拒绝；已知 minor 新增可选字段保持兼容。

这些 fixtures 是接口行为验证，不作为模型能力分数。

## 7. 版本与并行修改规则

各任务只修改自己的仓库。共享契约以本文件为 v0.1 起点；不在自己分支偷偷改公共字段含义。需要破坏性变更时先生成 `CONTRACT-CHANGE` 说明：原因、两边受影响模块、迁移与兼容方案，再由用户/协调对话同步。

首次集成前两边各自报告“已支持 / stub / 未支持”，锁定 adapter 版本或 commit；独立 fixture 通过后才做真实连接。不需要等两边所有愿望功能做完再集成。

## 8. Codex 与 Cursor 两种执行模式

目标与验收标准相同。差别仅是具体编码由谁执行，不能给 Cursor 版本降低验证要求。

每个可转交任务包至少写明：任务 ID、动机、当前文件/符号、前置依赖、允许改动范围、明确排除范围、输入输出契约、3—6 个行为验收条件、具体检查命令、交付文件、已知风险和退出条件。命令必须在目标仓库确认存在，不能把示意命令标为已验证。

建议让 Codex 重点负责：整体设计、恢复/幂等语义、评测泄漏隔离、实验协议、跨仓库契约及最终 review。可由 Cursor 承接：接口已定的 DTO/配置/报表/adapter 机械映射、故障 fixture、文档同步和局部重构。复杂度取决于实际改动，不能按工具品牌保证质量。

每批只交给一个实现者编辑同一组文件。Cursor 完成后由 Codex 检查实际 diff 和行为证据，必要时修复；不是只读它的完成摘要。两边都记录时间、模型开销、返工量，用户再决定下一批采用哪种方式；不能预先承诺一定省钱。

## 9. 首轮计划返回格式

1. 用自己的话说明项目最终是什么、明确不承担什么。
2. 当前代码中与目标有关的差距及文件位置，区分已存在、需修复、需新增。
3. 首个可交付版本的模块图和依赖顺序。
4. 不超过 8 个阶段，每阶段验收与可独立交付的产物。
5. 首批 2—4 个可由 Codex 执行、也能直接转交 Cursor 的任务包。
6. 资源与风险：本机支持情况、测试基线、模型实验预算待定项。
7. 对 v0.1 契约的冲突或修改建议。先列出可独立开展的工作，不因非关键缺失信息整体停摆。
