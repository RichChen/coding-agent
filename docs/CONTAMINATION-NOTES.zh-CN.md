# 数据污染说明与方法论（SWE-bench 子集）

> **定位**：本项目是 **harness 工程能力**展示（可控/可观测/可评测），**不刷 SWE-bench 榜**。本文档把「数据污染」从一个风险点，做成**可量化、可复现、可讲**的方法论组件。
> **证据**：`reports/contamination_probe.md`（+ `.json`）、`scripts/contamination_probe.py`、`reports/report_20260626T101113.md`（干净 A/B）。
> **结论先行**：本数据集存在**强 instance-level 记忆污染**（无上下文文件定位 54.2% 池化 exact、7/10 实例多数票命中正确文件）。因此**绝对成功率不可作为 agent 能力指标**；相对 A/B 在「污染对称」假设下仍有参考价值，但**区分度被压缩**。

---

## 1. 什么是污染，为什么 SWE-bench 尤其严重

**定义**：评测任务（及其答案）在模型训练时已被"看过"，模型可能靠**记忆**而非**推理**作答——相当于考前发了考卷和答案。

SWE-bench 这类基于真实 GitHub 的基准，污染是**双层**的，第二层无法回避：

1. **基准数据集本身公开**（HuggingFace `princeton-nlp/SWE-bench_Lite`），可能被直接爬进训练语料。
2. **更根本：底层 repo 才是污染源**。sympy/flask/requests 的 issue 讨论与对应**修复 PR/commit 全在公开 GitHub 上**，而 GitHub 是现代 LLM 的核心训练数据。即便把基准藏起来，模型也大概率"记得"这些 bug 怎么修。

两类记忆（*The SWE-Bench Illusion*, arXiv 2506.12286）：

- **instance-specific 记忆**：记住某个具体任务的 patch / issue 原文。
- **repository-bias 记忆**：过拟合到基准里那几个 repo 的架构模式——换个任务，只要还是 sympy 就"门儿清"。

---

## 2. 对本项目的精确影响（两层，勿混淆）

| 你测什么 | 污染影响 |
|---------|---------|
| agent 解决真实 bug 的**绝对能力** | **被毁**，数字虚高，**不可宣称** |
| planner vs baseline 等**相对 A/B** | 基本仍有效（污染对两边对称），**但区分度被压缩** |

**关键副作用**：若模型靠记忆就能解出部分任务，那不管什么 scaffold 都能解，planner 的差异被淹没——这**正是本项目反复看到 A/B CI 重叠、planner 分不出胜负的部分原因**（见 `reports/report_20260626T101113.md`：baseline 32% vs plan_act 24%，CI 重叠无显著差异）。

## 3. 本项目的证据

### 3.1 双峰通过率指纹（来自干净 A/B）

REWORK 干净 A/B 的 baseline per-task 呈**双峰**——`sympy-24213`、`flask-4992` 恒 5/5，一批 sympy 恒 0/5，中间梯度稀薄。这是"记得的就过、没记的就不会"的典型指纹（见 `docs/changes/SOLID-D1-REWORK-CLOSEOUT.zh-CN.md`）。

### 3.2 污染探针：无上下文文件定位（核心实验）

复刻 *The SWE-Bench Illusion* 的文件定位探针：**只给 issue 文本 + repo 名，不给任何文件树/代码**，让模型猜"该改哪个源文件"，与 gold patch 实际改动文件比对。一个没见过任务的模型不可能稳定说对仓库相对路径——高命中率即 instance-level 记忆铁证。

**方法学要点（两个被实验本身暴露并修复的坑）**：

1. **截断坑**：`deepseek-v4-pro` 是推理模型，会先在 reasoning 通道消耗预算再吐 `content`。初版 `max_tokens=256` 导致 6/10 答案被截断、被误记为"定位失败"——这是测量假象，不是模型答错。修复：提高预算 + 把 `truncated`（`finish_reason=length`/预算耗尽）单列，**不计入分母**。
2. **非确定性坑**：即便 `temperature=0`，该模型**两次同 prompt 给出不同答案**（推理链长度随机，长推理时会把自己绕错）。单次探针不可靠（单跑在 50%–78% 间晃）。修复：**每实例重复采样 N=5**，按命中频率聚合，并报告逐轮波动。

**稳健结果**（5 次重复、`max_tokens=2048`，详见 `reports/contamination_probe.md`）：

| 指标 | 值 |
|------|----|
| 池化 exact 率 | **54.2%**（26/48 次） |
| basename-or-better | **68.8%** |
| 多数票定位实例（≥basename） | **7/10** |
| 逐轮 exact 波动 | 50%–60%（重复后收窄） |
| 总成本 | ~5.3 万 token（相对一次全量 A/B ~59 万/任务可忽略） |

### 3.3 交叉印证与一个重要细分

- **双峰自洽**：恒过任务 `24213`（exact 5/5）、`flask-4992`（basename 5/5，知道是 `config.py` 只差 `src/` 前缀）都强定位，支撑"记得的就过"。
- **定位 ≠ 会解**：`23117`、`24909` 定位 exact 5/5，但 baseline 恒 0/5——模型**知道改哪个文件，却写不出修复**。说明 "恒 0" 的一批**不全是污染缺失，而是难度/scaffold 天花板**。这区分了"污染压缩区分度"与"真·能力失败"两类成因。
- **真·相对干净的任务**：`23262`（一致错成 `pycode.py`）、`23191`、`requests-3362`（一致错成 `models.py`）定位失败——这几个相对未被记忆。

## 4. 已采取的应对

1. **干净相对 A/B**：单变量（仅 mode/planner 不同）、防 402 余额污染、sympy 题面解法泄露清洗（见 REWORK-CLOSEOUT）。
2. **诚实标注**：本文件 + 报告中声明绝对成功率不作能力指标。
3. **污染量化**：探针把"污染有多深"用可复现脚本测出来，而非空口断言。

---

## 6. 结论

- **绝对成功率不作能力指标**——本数据集有强 instance-level 记忆污染（54.2% 池化 exact 定位）。
- **相对 A/B 在污染对称假设下仍有参考价值**，但区分度受限；解读时必须声明。
- 探针实验本身暴露并修复了"推理模型截断"与"temp=0 非确定性"两个测量陷阱——这正是本项目对"**评估有效性**"的方法论判断与工程能力体现。
